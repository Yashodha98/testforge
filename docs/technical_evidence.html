1. Professional, problem and evidence of need

Professional: “Nethmi” (declared pseudonym; real name and company withheld for anonymity, as promised on the interview sheet), Senior QA Engineer, healthcare software industry, at a company that builds and maintains a Hospital Management System (HMS) for a client in Saudi Arabia. Role and context: requirements are written in Confluence and tracked in Jira. A sprint has 5–6 epics with 5–8 user stories each. Evidence of need (from the answers): (1) test design takes about one working day per epic; (2) Cypress automation takes “normally 2 days”; (3) under time pressure “we do feature testing for happy path”, so negative and boundary tests are dropped; (4) ChatGPT was tried, but “we can’t get exact test cases”; (5) requirements are confidential and involve patient data; (6) to trust a tool, they want to compare it with the story scope and see that the test cases cover all scenarios.

Requirements: R1 (functional). From a Confluence requirements page, generate reviewable test cases for every user story and acceptance criterion, including negative and boundary cases, show coverage against the story scope, and export them to TestRail, in minutes instead of a day per epic. R2 (functional). From the approved test cases, generate Cypress automation scripts (one per story) that are checked before use, to shorten the 2-day automation effort. Constraints (from the interview): confidential and patient data (MRN, National ID/Iqama, phone numbers) must be masked before any AI call, and the tool must keep working when the AI is unavailable.

2. Emerging technology, justification and one alternative

Selected: generative AI / large language model (Anthropic Claude, model claude-opus-5-5, JSON output; Google Gemini also supported) applied to AI-augmented software testing. Why it fits: Confluence requirements are natural language. An LLM understands the intent of each story and can propose realistic positive, negative, edge and healthcare-specific scenarios (duplicate patient, invalid ID, wrong slot), write concrete steps with exact expected messages, and translate the tests into Cypress code. Nethmi’s complaint that ChatGPT gave “no exact test cases” is addressed by wrapping the LLM in classic test design: boundary values are computed exactly and given to the model, the output must follow a schema, and coverage of every AC is enforced and shown.

3. Architecture

4. Implemented connected features (Nethmi’s workflow: Confluence → TestRail → Cypress)

Step 1: Confluence document → test cases. Input: a Confluence page exported as Word (.docx, or Confluence’s MIME-based “Export to Word” .doc), PDF or HTML, or pasted text. Processing: extracts headings, lists and AC tables (PDF lines are re-joined); splits the page into user stories by story key (e.g. US-101) or “As a … I want …”; parses the criteria; computes exact boundaries (name 2–60 characters gives 1/2/3/59/60/61; ID exactly 10 digits gives 9/10/11); masks patient data; and asks Claude for JSON test cases per story, with the page’s context. It then validates, de-duplicates and tops up any AC the AI missed. Output: per-story coverage, an editable test table, a TestRail CSV and Gherkin files.

Step 2: test cases → automation scripts. Input: the test cases ticked in Step 1 (high priority or all). Processing: Claude writes one Cypress spec per story (Playwright optional), using data-cy selectors, Cypress.env() for credentials and exact expected messages. Each spec is checked with node --check, must contain describe/it blocks, and is rejected if it uses cy.exec, cy.task, child_process or eval. It is never executed. Output: validated US-101.cy.js … files in one ZIP. Connection: Step 2 only automates the tests the QA engineer approved in Step 1.

Error handling and fallback: a wrong file type, an empty file or one over 5 MB, a corrupt or password-protected PDF, a scanned PDF with no text, a legacy binary .doc, or a page with no stories each give a clear message and no AI call. A missing or invalid key, 429 quota error, timeout (60 s), network error, invalid JSON or zero valid items switches to the rule-based generator, with a visible warning. A partial AI answer is topped up per AC. An invalid or unsafe script is replaced by a template skeleton. Every test and script shows the engine that produced it.

7. Cost estimate and affordability (LKR, 1 USD ≈ LKR 300)

Assumptions (workload from the interview): about 5.5 epics per sprint with two-week sprints gives about 11 epics (≈ 70 stories) a month. Test design takes 1 day (8 h) per epic today. Each story needs about 1.5 AI design runs and one script. Measured with Claude Opus 5.5 on the largest sample story: ≈ 1.1k input + 8.5k output tokens per design run and ≈ 3.4k input + 14k output tokens per script (output includes the model’s reasoning). At the list price of USD 4 / 20 per million input / output tokens (verify current pricing), that is about USD 0.56 (≈ LKR 170) per story. QA time is costed at LKR 2,500 per hour. 8. Adoption / commercialisation approach

Path: (1) a two-sprint pilot on 2–3 HMS epics in Nethmi’s team, comparing design and automation hours, the number of negative and boundary tests, and defects found against manual epics; (2) an internal rollout with SSO, TestRail import and Cypress conventions, and later a Confluence API connector; (3) optionally, a Confluence/TestRail add-on for QA teams at Sri Lankan software houses, priced per QA seat. Who pays: the company’s QA/engineering budget. The saved QA days improve margins on the fixed-scope HMS contract. Main condition for proceeding: the healthcare client and company security must approve sending masked requirements to an external LLM under a data-processing agreement (otherwise a self-hosted model is needed), and the pilot must show at least 30% less design time, with at least 80% of AI tests accepted after review.
